## 1. 这是什么

自用媒体库管理器（中文环境，Windows），用来**替换已停更的旧程序**
`旧程序主程序`（易语言/EXUI 写的）。路线：**从零重写**，直接读现有
的库文件与图片目录，**不做数据迁移**。界面 MIT 独立实现（clean-room）。

- 技术栈：Electron 44.4.3 + `node:sqlite`（DatabaseSync）+ undici（`ProxyAgent` + 它的 `fetch`，
  因为全局 fetch 会忽略 dispatcher）+ 自定义特权协议 `shelfimg://`。
- 形态：文件夹版（zip）+ 单文件便携 exe，配置写在 exe 旁边。

## 2. 已定下、不再商量的决定

- **首次运行必须全空**：不偷偷继承旧配置；导入旧库列表需手动点按钮。
- **主题默认深色**（浅色作为设置里的开关）。发布用的 `config.json` 必须与之一致。
- **新数据只进 JavShelf 自己的库**，绝不往共享的旧库里加表。
- **验证不许碰 `网盘挂载点`**（云盘挂载库，慢）。**2026-09-24 更新**：允许对网盘
  （网盘挂载）做测试——v1.6.0 的预热实测就是在 `网盘挂载点` 上只读做的。
- **推送手动进行**：本机没有 gh CLI、没有配 git 身份。提交用一次性身份：
  `git -c user.name='JavShelf' -c user.email='javshelf@local' commit …`（不要改 git config）。
- **每次修 bug 都要升版本号**（固定要求）。
- **输出必须合规**：对话与日志里只报番号、字段名、计数，不写片名/类别等露骨内容。
- **界面文案里不能出现旧程序的名字**（含注释、字段值、目录名）。例外：旧库文件的真实文件名、
  以及库里的数据（有个演员名含 "Alexa Grace"，曾把措辞守卫误触发）。
- **README 与 CHANGELOG 里不用星号**（不加粗、不拿 `*` 当项目符号；列表用 `-`，强调用「」）。
  2026-09-25 明确要求过一次，此后新增内容照此写，别再往回改。CHANGELOG 顶部那一节
  「它是怎么走到今天的」是逐阶段的决策记录：**每出一版就补一段**，让人不看对话也能明白
  为什么长成现在这样。
- **功能不能依赖运行机器上装了什么**：包要发给别人用（"有些人没安装 potplayer"）。
- **数据目录（`cfg.dataDir`）是可选的，绝不能拿它当功能前提**：那是旧程序放它自己的库和旧图的
  那层目录；JavShelf 自己产生的一切写进 exe 旁边的 `JavShelf-data\`。UI 里要把这点讲明白。
- **覆写下载来的文件必须是明确同意**（v1.6.7 定的写法）：自定义封面默认只写 JavShelf 自己那一份，
  写进影片文件夹是裁切框里那个默认不勾的选项；勾了就先备份 `<同名>.bak`，「恢复」按 `.bak` 还原。
  目标是主进程按这条影片自己的文件夹算出来的，界面交不了路径。凡是「改磁盘上文件」的新功能，
  都按这个模板来：默认本地、覆写要勾选、覆写前备份、给一条能回到原样的路。
- **只读报告优先于「代为清理」**（v1.6.7 查重定的写法）：库里 `only_code`（文件夹）才是主键，
  同号两行就是盘上两份真拷贝，而 `Db.remove(code)` 按 `movie_编码` 删——一次删掉两份。所以查重
  只摊开事实（在哪几个库、哪个文件夹、实测多大），入口只有「打开所在文件夹」与「在墙上只看它」，
  一个字的库都不写；删谁留谁由报告呈现后决定。顺带定下一条：页面递一串路径让主进程读盘时，
  必须过「这个文件夹在启用库的目录下吗」那道检查（`dupes:detail`），不然报告就变成了任意读盘器。
- **「界面交来的路径」一律按来源收窄，不当成照办的地址**（v1.6.8 定下的口径）：能读文件的通道
  （`media:readAsData`、本地头像导入的目录/压缩包）只认这个窗口刚从原生选择框里返回的那批路径
  （一份 200 条的 LRU 名单）；能弹 shell 的通道（`reveal:file`）只认启用库根目录与 `JavShelf-data`
  底下的位置，并返回 `{ok:false,error}` 让界面把理由显示出来；能写库表的通道只认三个 `state_`
  字段，指名库没打开就报错而不是回落到第一个库。以后再加这类通道，先问「它的合法来源是什么」，
  别用「只有本程序的界面会调」当边界。
- **残缺的索引不能变成新的真相**（v1.6.8）：扫描里任何一个目录读不到，这份索引就保持待重扫、
  不写缓存盘、状态栏计入「N 处未读到」；删改刷新对落在这些目录底下的行只 shield 不删（界面写
  「待确认」）。理由很直白：网盘掉线一次，旧写法会把那一片当成「已被删除」。同理，预热失败、
  索引未重建、界面进程退出都必须留下一行日志，静默的降级等于没被发现。

## 3. 数据契约（磁盘布局）

- 旧库：`旧程序库文件`，表 `local_JAV`（影片行）、`data_list`（库定义）、`jav_idol`（旧女优资料）。
  状态字段取值是中文 `真`/`假`。`file_路径` 是 JSON：`{"视频文件":{"0":{"文件名":…,"扩展名":…}}}`。
  **只读**；唯一允许写回旧库的是 `state_收藏 / state_已看 / state_字幕`。v1.6.8 起这条由代码兜住：
  `Db.setState` 的白名单就这三个（以前还留着 `state_高清 / 进度 / 时长 / 观看`，那是本程序自己表里的列），
  播放对共享旧库也只写 `state_已看`，而且状态没写上不再让播放报失败。
- 影片目录：`<根>\<演员>\<条目目录>\`，里面是 `<片名>.mp4` + `<片名>-poster/-fanart/-thumb.jpg`
  + `<片名>.nfo`（Kodi `<movie>`，带 CDATA、`<actor>` 块，以及未知标签 `release`/`set` 要原样保留）。
- 条目目录**常常不是直接放视频的那层**，要下探到最里层（`deepestEntryDir`）。
- 当前实测数字：库 `JAV` 里 shelf_JAV **2029** 行（曾为 2030，有一条在磁盘上已不存在）、
  女优资料 **967** 位（其中 570 带身高/三围）、片商 238、系列 688、本地头像 **686** 张。
  发行包里的 `out/ship-data/JavShelf.db` 是 idol 966 / shelf_JAV 2030（打包时的快照）。
  **2026-09-26 复核**：同一批样本目录这一轮入库给的是 **2027** 行（第二库 **2275**，两库合计 4302），
  比上一版回归的 2029 + 2276 少 3 行——盘上少了目录，不是解析变了；这一段那几项是「发行包快照」口径，
  与回归 profile 的行数不必对齐。

## 4. 抓取现状（都是实测，别再重新试错）

- **JavDB 可用**（服务端渲染，不需要 JS）：`/v/<id>`（id 是短字母数字，如 `/v/k45bN`）、
  `div.movie-panel-info` 里带 片商/系列/日期/时长/演员；演员链接带 `class="actor-female"`，
  男演员没有 —— 这是排除男演员的可靠信号。`/makers/<id>`、`/series/<id>` 用 `class="section-name"`。
  **正则一定要限定在 panel 内**：导航栏也有 `/makers/xxx` 链接，曾经把"登入"解析成片商名。
- **演员目录分三支**：`/actors/censored`、`/actors/uncensored`、`/actors/western`，
  每支几百页（第 260 页仍是不同的人）。**只抓有码一支会导致一批演员永远绑不上**（v1.5.3 修）。
  翻页**过界不会返回空页**，而是重复最后一页 —— 结束条件必须是"与上一页 id 相同"。
- **限速**：200–350 ms 翻页会被边缘节点回 **502**（不是拦截页）。900 ms + 对 502/429/503 退避重试可用。
- **满屏 502 的头号原因是 Cookie**：一份过期/被标记的登录 Cookie 会让**每个端点**都 502
  （实测：带着它 3/3 端点 502，去掉同一请求 200 且解析出 50 人）。现在会自动去掉 Cookie 重试并写警告日志。
  **发布包里绝不带 Cookie**：`tools/package-zip.js` 会直接拒绝（除非 `--allow-cookie`）。
- **JavDB 匿名页面不再公布身高/三围**（列表页那个"身高"只是排序下拉的文字）。这些数字走
  **ja.wikipedia** REST `page/html` 的档案卡：生年月日/身長/スリーサイズ/ブラサイズ…
  **必须要求 `cm` 单位** —— 维基在公制行后面紧跟英寸行，只匹配数字会得到 35-25-36 当成厘米。
- **JavBus 是死的**（JS 验证；跟重定向会挂住，保持 `redirect:'manual'`）。FANZA `video.dmm.com` 不解析。
  旧的 `jvThumbs.csv` + `pics.dmm.co.jp/mono/actjpgs/` 头像路线已在 v1.3.6 整体删除。
- **Cookie 只能从本机 Chrome 取得**（v1.3.5）：内置浏览器打开站点是白屏；而会话 Cookie 是
  HttpOnly，页面脚本读不到；直接读 Chrome 的 Cookie 库也走不通（运行时独占该文件，新版还是
  app-bound 加密）。做法：用 **JavShelf 专用 user-data-dir** 启动真 Chrome +
  `--remote-debugging-port=0`，读 `DevToolsActivePort`，用 CDP `Storage.getCookies` 取回。
  Chrome 136+ 对**默认**配置目录禁用调试端口，所以必须用独立目录（不是偷懒）。

- **女优头像地址可以从编号直接推出来**（v1.6.4，2026-09-22 存下来的真实女优页验证：
  编号 `W1EGe` → `https://c0.jdbstatic.com/avatars/w1/W1EGe.jpg`）：前两位小写当桶、文件名保留原
  大小写，和封面 `/covers/<2>/<id>.jpg` 同一套规则。所以手动绑定哪怕没抓到 `<img>` 也有地址可用。
- **手动绑定 JavDB（v1.6.4）走「只取编号」这条路**：粘进来的整条地址（镜像域名、`/actors/<id>/名字`、
  `?page=` 都算）只用正则取出编号，之后的请求一律重组成 `https://javdb.com/actors/<编号>`，
  头像地址只接受 `*jdbstatic.com` 域名——**不要**改成直接抓界面粘进来的 URL，那是给 SSRF 开门。
- **绑定一个人要动两张表**：`idol` 上的 `javdb_id/javdb_url` 只是她自己那一行；
  「下载官方头像」和侧栏圆圈读的是 `actor_index`（按 javdb_id 查），漏写这一步就会出现
  「编号明明绑上了，头像永远下不来」。`idols.patch` 只写抓取那一组列，`idols.save` 只写资料列，
  两边互不覆盖——这是设计，别顺手合并成一个 upsert。
- **批量 `bindFromIndex` 只填 `javdb_id=''` 的行**，所以手动绑定不会被下一次整库重抓冲掉。
- **ja.wikipedia 的档案卡是「一份数据出现两遍」**（v1.6.5 实测）：REST `page/html` 里既有渲染行
  `公称サイズ（ 2024年 時点） 身長 / 体重 160 cm / ― kg スリーサイズ 98 - 70 - 104 cm ブラサイズ H
  英米単位系 … 39 - 28 - 41 in`，也有模板留的机读尾巴
  `時点 : wt : 2024年 , 身長 : wt : 160 , バスト : wt : 98 , … カップ : wt : H ,`。
  机读尾巴不是人人都有（明里つむぎ 就没有），`カップ : wt : ,` 也可能是空的（深田えいみ），
  这时才退到渲染行的 `ブラサイズ`。**一个人可能有两段不同年份的**，所以按 `時点` 取最新那段。
  出身地 `日本 ・ 愛知県 豊橋市` 这种带间隔号和角标的要清洗，收之前要求它像地名（都/道/府/県/市/区
  或 2–8 个中日文字符，且不含 `a-z:` —— 机读尾巴的碎片 `:wt:・愛知県豊橋市,` 就是这么被剔掉的）。
- **连读维基会被 429 挡**（v1.6.5 实测：第 8~10 个请求开始，带 `Retry-After: 2`；404 才是真没有
  这一页）。以前 429 被当成"维基没这个人"，整批人报缺失看起来像解析器坏了。现在按 `Retry-After`
  退避重试，且抓取阶段人与人之间停 1.2 秒。
- **旧程序的 `jav_idol.cup` 是枚举下标，不是字母**（v1.6.5 实测）：库里分布 565 条数字 / 41 条字母 /
  5 条「字母+底围」（D65、E65、F65）/ 361 条空。拿同时有 JavDB 编号的人对过去，`1=A … 13=M`，
  13 档里 11 例完全吻合，差的 2 例是身体数据的不同时点。现在盘上只存一个大写字母，
  `normCup()` 一处定义、写入/导入/排序/显示四处共用；存量由启动时的 `repairLegacy()` 一次换算（幂等）。

## 5. 反复踩过的坑（每条都花过一轮以上）

- **V8 里 `/[\\/]/` 匹配不到反斜杠**。可用的写法：`/[\/\x5c]/`、`/[\x5c/]/`，或干脆
  `s.includes(String.fromCharCode(92))`。这个坑出现过两次：一次让"覆写 nfo"永远失败（Windows
  绝对路径被判成相对路径），一次让新写的回归断言误判。
- **`entryFor()` 返回的是给渲染进程用的 `r<n>/…` 引用**（`shelfimg://` 专用），**不能直接交给 `fs`**
  —— 否则路径会拼到 exe 目录上（v1.5.4 的 ENOENT）。要真实路径必须过 `nfoPathFor()` / `media.resolve()`。
- **回归断言写弱了等于没写**：以前只断言 `entry.nfo` 非空，而 `r3/…` 也是非空的，所以这个 bug
  连着"测过"发了两版。断言要断"绝对路径 + 文件真的在盘上 + 不是引用"。
- **`SMOKE_FAIL` 曾经仍以退出码 0 结束**，脚本看不出失败（v1.5.1 起置 `process.exitCode=1`）。
  判断回归是否真的通过，要看有没有 `SMOKE {…}` 那行完整 JSON，别只看 EXIT。
- **nativeImage 解不开某些极小的 PNG**（一个 79 字节的测试 PNG 直接 `isEmpty()`）。测试图片要用
  画布导出的 PNG，也就是裁切对话框真正发出去的格式。
- **`db.exec('ATTACH DATABASE ? AS src')` 里的 `?` 不会绑定参数**（exec 不支持），会静默挂上一个
  空库；要用 `db.prepare(...).run(path)`。
- **性能**：逐行 commit 让库切换从 251 ms 变成 11.7 s（`entities.rebuild`）；批量写一律包事务
  （`idols.patchMany` 同理）。
- **封面就绪时间**要用**视口内相交**的卡片统计，整页统计会被 lazy 加载骗（曾误报 29/96）。
- **Git Bash 会改写命令行**：`$_` 被展开成 `extglob`、`/B` 被当成路径。要跑 PowerShell/robocopy
  就把脚本写成 `.ps1` 用 `-File` 调用。
- **单实例锁**：在本机跑第二个实例要用 `--user-data=<目录>`；别去 kill 正在运行的 JavShelf。
- **预热判定线必须比懒缓存判定线高一档**（v1.6.0：250 ms vs 600 ms）：判错懒缓存只多存一份，
  判错预热会把整个本地库（G 根 5978 部）复制成双份。回归里真抓到过一次污染：满载时本地
  4 KB 读飙到 266 ms。规则=「一次快读即整根跳过」，别看两份均值。
- **固定 sleep 的回归会和后台预热抢磁盘**：`coverEdit` 的 900 ms 等待在预热跑着时不够，
  已改轮询。新写界面断言一律轮询，别赌 sleep。
- **缓存了图片文件 ≠ 缓存了图片路径**（v1.6.0→1.6.1 的教训）：入库行存着绝对目录，
  `entryForUncached` 原先优先对目录做**同步 readdir** 来发现 sidecar——网盘挂载实测
  170-250 ms/次，一页 120 行 = 主进程冻结半分钟，海报照样全空。海报路径的唯一正确来源
  是内存扫描索引（一次扫盘答完所有行），readdir 只作索引 miss 的兜底。
- **扫描索引签名（根目录 mtime）一变就从空索引重扫 = 整面墙「未索引」**：往网盘根目录
  加新片就会变。v1.6.1 起过期索引先顶上、后台刷新（smoke `staleIndex` 强断言）。
- **主进程里对网盘的一切同步 I/O 都是冻结**（statSync 除外,网盘 stat ~0 ms）：协议层
  原盘读、nfo 原盘读在 1.6.1 起全部 await fsp。新代码触碰 `X:` 一律用异步。
- **`capturePage()` 拿到的是上一合成帧**：截图前必须轮询等图片 `complete && naturalWidth>0`
  再补一点余量，否则截出来的是「上一个状态」，会把自己骗过去（v1.6.2 诊断时连截错两张）。
- **默认封面只查「最早一部」= 大量黑色占位框**：老片常常没有海报文件，同一实体后面几十部
  都有。v1.6.2 起墙按日期序回退找前 12 部（批量 resolve，不多走磁盘）；框比例 2:3 与海报
  一致 = cover 精确铺满、零裁切零黑边（女优墙 3:4 不动，那边是方形头像）。
- **smoke 窗口被挡住 = 回归无限挂起**：`scroll` 一类步骤靠 `requestAnimationFrame` 推进，
  窗口不可见时 Chromium 直接停发 rAF，await 永不返回（run22 就这么卡了十分钟，日志一个字不吐）。
  v1.6.2 起 SMOKE 模式 `ready-to-show` 里 `setAlwaysOnTop(true)` + `focus()`。在用的 JavShelf
  挡在前面时别去 kill 它，换个 `--user-data=<新目录>` 跑就行。
- **但别把测试窗口置顶**：1.6.2 那么改之后，测试窗口被其他窗口盖住并被手动关掉 → 整轮回归
  静默退出（EXIT=0、日志只剩 `\r\n`，看着像程序自己没了）。v1.6.3 起改
  `win.setBackgroundThrottling(false)`：被遮挡照样出帧，不抢屏。判断「没输出」之前先看
  `out/smoke.log.txt` 最后一行 `-- next: <步骤> done`，那才是进度真相。
- **`Compress-Archive` 压不动刚复制出来的 1.3 GB 数据包**：Defender 还攥着 `imgcache` 里刚写入
  的文件句柄，它撞上第一个就整体中断（`文件正由另一进程使用`），本身还慢。大包改用系统自带
  `tar.exe`（bsdtar），并且**压完要核对条目数**——它遇到占用文件是跳过而不是报错，静默少文件。
- **bsdtar 把 `G:\…` 当成「远程主机:路径」**：报 `Cannot connect to G: resolve failed`。
  要么加 `--force-local`，要么 `cwd` + 相对路径。
- **robocopy 是 `<源目录> <目标目录>` 两段式**，不是 `cp 源 目标` 那种三段写法；写成
  `源 叶子名 目标` 直接返回 16（severe error）。
- **带运行中的库要拷哪几样**：`JavShelf.db` + `imgcache` + `actor` + `scan`（+ `javdb-chrome`
  共 890 MB 左右），Chromium 自己的 `Cache/GPUCache/DIPS/Local Storage/…` 不带。程序还开着，
  所以库文件是「拷 → `PRAGMA integrity_check` → 不过就重拷」，别裸拷。

- **一个 `#modalHost` 只放得下一个对话框**：`modal()` 一进来就清空宿主，所以在「编辑女优信息」里
  再开一个「绑定 JavDB」弹窗会把正在填的表整个吃掉。v1.6.4 的绑定块因此是**内嵌**在编辑弹窗里的
  一行，不是二级弹窗。要给别的界面加编辑能力，先想清楚这一点。
- **回归里按位置选输入框（`ins[3]`）早晚会给后来加的那一行让位**：v1.6.4 给编辑弹窗加了 JavDB
  输入框，`idolEdit` 的 `ins[3]` 就从「身高」变成了「中文名」。现在弹窗里的输入框都带
  `data-field="<列名>"`，断言一律按字段名选。
- **拿不联网的东西去测联网的功能 = 白测**：`idolBind` 步骤跑在没有代理、不碰 JavDB 的档案里，
  所以它验的是"乱输入给可读提示 / 没代理说缺代理 / 绑定写库并且导航条跟着变 / 索引里查得到她"，
  而不是"能不能抓到日本人的头像"。真站短测在 `--smoke-crawl` 那一支，别混在一起。
- **`if (opened) { … }` 这种"检测到就顺手测"的回归会静默变成空步骤**：`idolEdit` 右键之后直接数
  输入框，从来没人点菜单里的「编辑资料」，于是 `opened` 恒为 `false`、保存从没跑过，却连着好多版
  报"全绿"（结果行里那个 `opened:false` 一直就在日志上）。写断言的规矩：**不满足就 throw**，
  别把失败降级成返回值。
- **`ipcRenderer.invoke` 的 reject 自带一层壳**：`Error invoking remote method 'x': Error: <正文>`。
  主进程 handler 抛的是给人看的中文句子，直接 `+ e.message` 就会把这层壳贴到界面上。
  renderer 里有 `errText()`（app.js）剥掉它，界面上的报错一律走它。
- **收敛到单一来源的时候要问清楚「谁负责它们全部存在」**（v1.6.6）：`LibraryFiles.prepare(dirs)` 会把不在
  本次 `dirs` 里的根全部删掉，而启动是按库逐个 `startScan` 的——第二个库准备完，第一个库的三个根就从索引里
  消失了。症状只在播放上暴露，因为 `entryFor()` 还留着「按入库行存的目录现场定位」的退路，而 `player:open`
  绕过它直接问索引。现在：`prepare` 只在调用方给出 `keep`（全部启用库的根）时剪枝，播放与海报共用 `entryFor`。
- **回归里「取到值」不等于「文件在盘上」**：`locate` 步骤长期只看 `resolve()` 的返回值非空，于是多库踢索引这个
  bug 连着好多版都是绿的。现在把抽样的视频路径全部拿回主进程逐条 `fs.existsSync`，并要求抽样覆盖到两个库；
  `scanStat` 也从「计数 > 0」改成「每个启用库的每个根都在索引里、`entries>0`、且不在扫描中」。
- **渲染层的 `el(tag, cls, text)` 只接受三个参数**（v1.6.5）：`el('div','row', a, b)` 里第四个子节点
  被静默丢掉，而第三个参数如果是元素会被写成 `[object HTMLLabelElement]`。要挂多个节点必须
  `const line = el('div','row'); line.append(a, b);`。「从日文维基补全」按钮就是这么"代码里明明
  append 了、DOM 里永远没有"的。
- **新加的列属于哪一族要当场决定**（第二次踩了）：`idols.js` 里 `FIELDS` 由 `save()` 写、
  `EXTRA` 由 `patch()/patchMany()` 写（`open()` 负责 ALTER 建列）。`note` 属于 `EXTRA`，
  所以抓取阶段那句"记一下出处"用 `save()` 写了好多版，一次都没进过库。本轮把 `birth_place`
  同时放进两族（编辑弹窗走 save、抓取兜底走 patch），并在启动做一次迁移。
- **模板字符串里写的注释不能带反引号**（v1.6.7）：smoke 的每一步都是 `js(\`…\`)`，注释里那句
  「`r<n>/…` 是相对库根的引用」把模板提前闭合了，整个 smoke.js 变成 `SyntaxError: missing ) after
  argument list`。而 Electron 里 `require('./smoke')` 抛出来只是一行 `UnhandledPromiseRejectionWarning`，
  窗口照常开着、`out/smoke.log.txt` 停在最后一步——看起来像"卡在中间"，其实是文件根本没进去。
  规矩：`js()` 里的中文注释一律用「」，改完 smoke 必须先 `node --check main/smoke.js` 再启动。
- **「引用」不能拼在条目目录上**（这一族第三次踩，v1.5.4 / v1.6.6 / v1.6.7）：`entry.poster` 给的
  `r<n>/…` 是相对**库根目录**的，而 `entry.dir` 已经在库根下面了，`path.join(dir, rel)` 拼出的是
  双层路径。要真实路径只有 `media.resolve(rel)` / `nfoPathFor(entry)` 两条正路。回归这一版改成直接问
  主进程 `cover:videoTarget` 要写入位置，而不是在 Node 侧重算——测试和生产用同一个答案才不会
  "测试自己错"。
- **报告要用的值得在它被消耗之前记下**（v1.6.7）：`videoCover` 那一步的报告字段写成
  `sha(bakAbs) === originalSha || !fs.existsSync(bakAbs)`，看着有兜底，其实 `sha()` 先执行——而
  `.bak` 已经被上一步「恢复原本封面」用掉删掉了，于是所有断言全绿、报告自己 ENOENT，整轮 13 分钟
  回归白跑。改成在 `.bak` 还在的 `retain` 那一步就把哈希记进变量。
- **给人看的时间不能用 `toISOString()`**：日志面板用它取时分秒 = UTC，在本机比墙上钟点差八小时，
  结果"日志和刚才的操作对不上"。规则：写给人读的戳用本地时/分/秒，排序与存储用 UTC，别混。
- **同一个循环里两步都保存同一行，后一步必须用前一步的结果**（v1.6.5）：JavDB 那一步刚把身高写进去，
  维基那一步还拿着进循环前读的旧快照再 `save()` 一次，刚填的值被空值覆盖回去——不报错，只是数据
  又没了。行对象要在两步之间往下传（`let p = p0`）。
- **「保存」类按钮要证明它真的写过盘**（v1.6.8，五版假绿）：`nfo:write` 的 handler 收的是
  `{rel, fields}`，而界面发的是 `{fields, actors}`——演员那一族在通道上被静默丢掉，于是「保存 nfo」
  改得动片长、改不动演员，且因为原字节没变连 `.bak` 都不生成。回归那一步只读不写，所以五版没人发现。
  规矩：凡是「编辑框 → 保存 → 回读」的功能，回归要写一次真的（改一个值 + 加一条列表项）、在**盘上**验、
  再逐字节还原。两端字段名不同名就是 bug 的温床，别在中间层做"选择性转发"。
- **「覆写之后再写回原值」不等于回到原样**（v1.6.8）：`writeNfo` 的 `setActors` 会把所有 `<actor>`
  块剥掉重发（顺带归一缩进），而 CDATA 那族本来就不保序——实测 48 个真实 nfo 里 `plot` 有 29 个
  round-trip 之后字节不同（`runtime` / `premiered` 52/52 一致、`studio` 51/52）。所以断言里的还原
  必须先把原字节读进变量、结束时拿它 `writeFileSync` 回去，绝不能指望"再写一遍原值"。
- **等待一个请求完成，只有两个诚实信号**（v1.6.8）：按钮重新可用 + 结果行不再是「正在…」。
  `idolBind` 那一步原来读的是"提示文字变了没"，而它把所有 `.bindrow .hint` 拼在一起——同一个编辑
  对话框里还有第二块 `.bindrow`（维基补全）和一行静态状态文案，于是偶尔拿另一块的旧文案判成败，
  报一句"乱输入没给出可懂的提示"。定位到那一块、取它最后一个 `.hint`，才算在等对的东西。
- **只报数不断言的步骤迟早绿得没有意义**（v1.6.8）：`scroll` 长期把帧率塞进报告而不判成败，窗口被
  挡住时 rAF 一秒出一帧照样通过，README 里那个 112.5 FPS 就是从这种样本上抄的（挨饿的两次实测
  1.3 / 4.3）。现在把 >200 ms 的帧算停顿，出帧占比不到八成或中位帧比 60 Hz 慢一半就作废重采，
  三次都拿不到可信样本直接失败。数字宁可没有，不能是假的。
- **响应头 `immutable` 只能给「字节变了就换文件名」的资源**（v1.6.8）：头像是一位演员一个稳定文件名、
  覆写式的，于是本地缓存副本 + 一年期强缓存换完头像之后一直看到上一张（浏览器和这个进程都按
  URL 缓存）。现在 `actor/` 这一类完全跳过图片缓存、响应头 `no-cache`；海报与手工封面因为文件名带
  内容哈希，继续吃强缓存。**给任何缓存策略分类之前，先问这个位置会不会原地换内容。**
- **「窗口关掉就退程序」会把崩溃伪装成跑完了**（v1.6.8）：两次回归退出码 0、日志停在上一步，
  事后判断只剩"渲染进程没了"这一个解释，而当时没有任何一行字说到这件事。现在 `render-process-gone`
  写日志，smoke 下直接 `SMOKE_FAIL` + `process.exitCode = 1`；`unresponsive` / `responsive` 也各留一行。
  另：一个宿主只装一层模态，关掉必须把宿主清空——以前那个对话框的按钮关掉之后仍然能 Tab 到。
- **「问过」和「有结论」在缓存里是两件事**（v1.6.8 查重体积）：整批问失败（库刚改过、网盘掉线）只记
  `dupeAsked`（格子写「未测到」、下次开窗口重问），只有主进程明确答过的那一行才进 `dupeFacts`。
  否则一次掉线就把「读不到」钉成这一轮的真相。
- **CSS 里定义的变量要和用到的变量对一遍**（v1.6.8）：`--muted` / `--panel` / `--sunk` 在二级界面与
  封面墙上用了很久，从来没定义过（颜色全靠 fallback）；`.hint` 在文件末尾被重复定义了一次，
  把 11.5px 顶成 12px。这类不一致在截图里几乎看不出来，只能靠审。
- **「原地换内容」的资源必须让 URL 跟着字节变**（v1.6.9）：头像是一位演员一个固定文件名，
  上一版虽然把它从 `immutable` 换成了 `no-cache`，但换完仍然要重启才见效——因为界面只是重画一次，
  重发的是同一个 URL，而浏览器与协议层都按 URL 缓存那张图。现在版本戳由 `ActorStore.refOf()`
  从真实文件的 mtime 取（`?v=`），只在主进程出口和实体行离开 `ipc-media` 时贴上；界面自己
  不拼戳、也不从数据库读带戳的路径（库里存的一律是干净 rel）。
- **协议层看不见 query，`img.src` 又会把 CJK 路径百分号编码**（v1.6.9 断言踩的坑）：
  `shelfimg://` 的 handler 只按 `decodeURIComponent(url.pathname)` 找文件，所以带 `?v=` 不会 404，
  但回归里拿 DOM 的 `src` 和主进程给的 ref 直接字符串比对必然不等（一个是编码过的、一个不是），
  比之前要先 `decodeURIComponent`。同时 `js()` 模板里反斜杠只剩一层：`/\d/` 写进去变成 `/d/`，
  于是那一步一度报「三段版本号全 0」——**断言自己算错也会伪装成功能没修好**，先用一次性探针
  把主进程真实返回值打出来再改代码。
- **托盘这类系统菜单要先能被读回来，才谈得上断言**（v1.6.9）：Electron 44 的 `Tray` 没有
  `getContextMenu()`，模板塞在 `setContextMenu(Menu.buildFromTemplate([...]))` 里就再也拿不出来。
  抽成 `trayTemplate()` 并交给 smoke，验的才是真实托盘用的那一份；顺带把「重启软件」这条整条
  走通：`--smoke-restart` 往自己的 profile 写一次性 nonce → 按菜单同一条路（`restart()`）重启 →
  子进程靠继承来的环境变量认出这是自己的重开、回读 nonce 与启动状态。重开发起的进程是脱离父进程的，
  所以结果只能写文件，不能指望 stdout。
- **一个界面对某个设置生效，不等于所有界面都生效**（v1.7.0 的 bug）：顶栏「排序」的比较器一直写在
  `applyFilters()` 里面，只对 `state.view` 跑；三级界面（单个女优的作品列表）在 `paintEntityFilms()`
  里从 `state.rows` 自己 filter 出一个新数组，那条路径根本没经过比较器——所以截图里那个下拉框
  换什么都是库顺序。**凡是"从同一批数据里另挑一条流水线"的界面，都要回头确认共享逻辑还在不在。**
  现在收成一份 `sortRows(rows)`，两处共用；`paintEntityFilms` 拿到的是 `filter()` 的返回值，
  就地排序不会把 `state.rows` 打乱（回归里专门断言首行没变）。
- **断言要点真正有信息量的那一屏**（v1.7.0 第一步就假失败）：二级封面墙按名字排且只画前 400 格，
  点第一格落在一位只有一部片的女优身上——四种排序看起来一模一样，`distinctOrders` 只有 1。
  改成从数据里挑作品最多的那位（168 部）再进她的屏，顺序差才看得见。**测顺序就要在顺序有意义的
  样本上测**，不然断言只是在证明"这一屏只有一格"。
- **同一个 `scrollTop` 值再写一次不产生 scroll 事件**（v1.7.0 顺手修的老断言）：瀑布流那步滚到底
  加载完，宿主高度不变时二次赋同一个值直接没有事件，等 6 秒 TIMEOUT，实测卡在 24 → 48 → 48。
  先往上抬 120px 再压到底才有第二发。
- **元素上的 `object-fit: cover` 会在变换之前先把图裁掉**（v1.7.1 的根因）：裁切框的 `.cropview img`
  铺满 260×347 的框，横图左右两侧在元素内部就不存在了，之后 `transform: scale()` 拉多小都只是在放大
  那条已经裁过的窄带——**看着是缩放救不了的事，先怀疑裁发生在哪一层**。改法是几何收回 JS：元素按
  cover 尺寸真实排版（`layout()`），由外框的 `overflow: hidden` 负责裁剪，元素上只留 `contain`。
- **一份几何只能有一个出口**（v1.7.1）：预览的 `transform`、拖动边界、导出画布的 `drawImage` 三处
  都从 `mapping()` 取同一份 `s = cover * scale`。分开写就会「框里看到的是 A、存出去是 B」，
  而且这种偏差只在特定缩放档位出现，截图看不出来。判据同理：`whole = fit / cover` 是缩放下限
  （= 整图可见），把它锁在 1 就等于删掉了「看全图」这一档。
- **滚轮要给模态框里的可拖区用，必须 `{passive:false}` + `preventDefault()`**（v1.7.1）：
  `.modal` 自己 `overflow-y: auto`，不拦事件的话滚轮在滚对话框而不是缩放。合成 `PointerEvent`
  走 `setPointerCapture()` 会抛（指针不属于这个事件），要么包 try，要么拖动断言别依赖捕获。
- **等 URL 变了不等于图出来了**（v1.7.1 的假失败）：`avatarLive` 三段版本号严格递增、按新 URL
  `fetch` 回来 200 / 1361 字节，可侧栏那张 `<img>` 还在解码（`decoded:false`）——等待条件要同时看
  `complete && naturalWidth > 0`，也就是「页面真的画出尺寸了」，而不是只看 src 或只看 HTTP 状态。
  这和 v1.6.8 那条「文字变了 ≠ 请求完成」是同一族。
- **两个 smoke 实例会抢同一份 `out/smoke-profile`**（v1.7.1 自伤一次）：一轮还在跑就又起一轮，
  第二轮开头 `fs.rmSync(PROFILE_DIR)` 把第一轮正在写的档案清掉，两轮结果都作废。跑之前先确认
  没有活着的 electron 回归进程；清理只 kill 命令行里带 `Javself` 的 electron.exe，别碰用户在用的
  `JavShelf.exe`。
- **挨饿挡板的正常触发不是代码回归**（v1.7.1 两轮）：`scroll` 报「60 帧 / 出画 0 / 停顿 60」时，
  先想窗口是不是被挡住或屏幕锁了（`requestAnimationFrame` 不再推进），换到前台重跑；判据是
  `tries` 与 `stalls`，不是「这一步失败了 = 程序变慢」。

## 6. 怎么构建、测试、交付

```bash
npm install --registry=https://registry.npmmirror.com
npm run smoke                                   # 端到端回归（49 步），从空配置开始
electron . --smoke-reopen --user-data=out/ship-check   # 二次打开：直进海报墙 + 抽样 nfo 是否真在盘上
electron . --smoke-crawl --user-data=out/crawl-profile # 真站短测：三支目录 + 绑定 + 下 5 张头像
electron . --smoke-restart --user-data=out/smoke-profile # 托盘「重启软件」的往返：新进程要认回同一个档案
npm run zip -- --config=out/ship-config.json --data=out/ship-data   # 文件夹 + zip（带配置与已入库数据）
npm run zip                                                        # 只出干净空包（首次运行全空）
node tools/build-data-package.js [--zip-only]                       # 在干净包基础上带上真实数据
node tools/verify-data-package.js                                  # 只读核对：表行数 / 文件数 / config 一致
node tools/build-portable.js --skip-unpacked    # 单文件 exe（先把 config.json 与 JavShelf-data 放进 release/win-unpacked）
```

交付纪律（固定流程，别省）：
1. 交付前先看有没有实例在跑：`Get-Process JavShelf`。**绝不覆盖正在运行的那份**。
2. 复制到 `G:\<交付物目录>`，文件名带版本号（新版本是新文件名，不会撞）。
3. 两侧 `Get-FileHash -Algorithm SHA256` 比对，报告里给绝对路径 + 字节数 + 哈希。
4. 本地提交（一次性身份），推送手动进行。
5. 分支：`main` 是交付过的版本线，后续功能在 `dev` 分支内部开发，稳定后并入 `main`。
   上手与推送说明见 README。
