# JavShelf

本地 JAV / 视频媒体库管理器：读影片文件夹里的 `.nfo` 与 `-poster / -fanart / -thumb.jpg`，
建海报墙，双击直接播放本地文件。为替换一个已停更的旧程序（易语言/EXUI 写的）而从零重写：
路线：「直接读现有库文件与图片目录，不做数据迁移」，界面 clean-room 自行编写，MIT 许可。

当前版本 v1.7.1（2026-09-26）。发布形态：文件夹 + zip，另有单文件便携 exe。
不想折腾的，直接到 [Releases](../releases) 下载 `JavShelf-v1.7.1-windows-x86_64.zip`，
解压即用（干净包：不含任何库数据、Cookie 与登录凭据，首次运行是空库）。
每轮施工记录与决策原因见 [CHANGELOG.md](CHANGELOG.md)；
当前状态、已定决策、抓取实测事实、踩过的坑与待办见 [docs/状态.md](docs/状态.md)。

## 运行环境

- Windows x64（也只在 Windows 上验证过）。
- 开发：Node 24（用到 `node:sqlite` 的 `DatabaseSync`，这是选 Electron 44 的硬前提）。
- 运行时：Electron 44.4.3 + undici（`ProxyAgent` + 它自带的 `fetch`，全局 fetch 会忽略 dispatcher）。
- 图片通过自定义特权协议 `shelfimg://` 交给渲染进程；程序自己产生的一切数据写在 exe 旁边的
  `JavShelf-data\`，不依赖也不写入旧程序那层数据目录。

## 怎么跑

    npm install --registry=https://registry.npmmirror.com
    npm start                                        # 跑源码
    rm -rf out/profile-smoke && npm run smoke -- --user-data=out/profile-smoke
                                                     # 端到端回归（49 步），从空配置的首次启动开始
    npx electron . --smoke-reopen --user-data=out/profile-smoke
                                                     # 复用同一 profile：第二次打开必须直进海报墙
    npx electron . --smoke-crawl --user-data=out/crawl-profile
                                                     # 真站短测：三支演员目录 + 绑定 + 下 5 张头像
    npx electron . --smoke-restart --user-data=out/profile-smoke
                                                     # 托盘「重启软件」的往返核对：重启后要落回同一个档案
    npm run zip                                      # 文件夹 + zip 发布物（推荐）
    npm run zip -- --config=<配置> --data=<运行数据>  # 带着已入库数据发布（含 Cookie 的配置会被拒绝）
    node tools/build-data-package.js                 # 在干净包基础上换成真实数据（拷后校验）
    npm run dist                                     # 单文件便携 exe
    npm run icon                                     # 重画 build/icon.png

要开第二个实例（或做测试）必须带 `--user-data=<目录>`，否则会撞上单实例锁。
`out/`、`release/`、`dist/` 都是本地产物，不进版本库。

## 主要能力

入库与多库

- 每个库指向一个影片文件夹，添加后自动读 nfo 建库；三种刷新（新增 / 删改 / 覆盖），
  进度实时显示（已扫 / 发现 / 新增 / 更新 / 删除 / 跳过 + 当前目录）。
- 库各自有开关，关掉即从海报墙消失；首次运行完全为空，导入旧库配置需手动点按钮。
- 「从库中删除（不删文件）」只删 JavShelf 自己表里的一行；存在旧程序共享库里的库一律拒绝删。
- 顶栏「查重」出一份只读报告，两层分开报：完全重复（同一个番号落在两个文件夹，跨库也算，
  组头写明「几个库」）与近似重复（ABP-123 / abp123 / ABP-0123 归一后同号）。每一处列出所在库、
  文件夹末两级与该文件夹的实测视频体积，给两个入口：打开所在文件夹、在墙上只看它。
  分包写法 ABP-123-2 / ABP-123A 归一后仍然不同，不会被误判成重复。
  分组在页面内存里跑（行本来就全在手上），体积那一路由主进程读盘，只允许读启用库目录下面的
  文件夹。它不删文件、不改库：同号两行是真的两份拷贝，不做自动取舍。

浏览

- 虚拟化海报墙（高分屏矢量渲染，DPI 感知），左侧分面：演员 / 类别 / 系列 / 番号 / 年代，
  演员列表支持特色排序（作品数、名字、身高、年龄、罩杯、胸围、腰围、臀围）与升降序。
- 瀑布流是真正的无限加载：滚到距底部 600px 续下一批并追加，不再显示误导性的页码。
- 顶栏搜索、排序、卡片大小、显示设置（按视图分别配置）、日志面板（500 条环形缓冲）。
  排序只有一份比较器：主页海报墙、单个女优 / 片商 / 系列那一屏作品列表都吃它，改一下当场重排。
  三面的封面墙不吃它——那一屏的顺序由墙自己说明的规则决定（作品数、名字，或侧栏那组特征 chip）。
- 详情侧栏：元数据、演员（右键可编辑）、剧照条带与大图、播放 / 收藏 / 已看 / 打开目录 /
  复制路径 / 编辑 nfo / 在浏览器中打开 / 从 JavDB 覆写 nfo。
- 右键任意一张卡片 → 「导入图片裁切为封面…」：默认只换 JavShelf 自己显示的那一份（存在
  `<数据目录>\video_cover\`，影片目录一个字节不动），裁切框里勾「同时写入影片文件夹」
  才会覆掉影片旁边那张 `-poster.jpg`，覆之前先原样备份成 `<同名>.bak`。「恢复原本封面」删掉
  本程序那一份并把 `.bak` 还原回去。
- 那个裁切框（单部封面、演员头像、片商 / 系列封面共用一个）是 3:4 的固定框，横图与超长图靠
  「看全图」整张摊开（缩放下限就是这一档，实测 1200×150 的图能拉到 9.4%）、「填满框」回到铺满；
  滚轮在指针所在位置缩放，按住拖动能挪取景，拖不出黑边（图比框窄的那根轴锁在中心）。
  框里看到的与存出去的读同一份几何，所以任意缩放档位下两者逐像素一致。图解不开时框里直接写原因
  （多半是过大或格式不支持），不会静默存出一张黑图。

二级界面

- 女优 / 片商 / 系列三面封面墙，点格子进单个实体的作品列表，视图栈逐级返回。
- 封面可编辑：候选取本库影片封面（按发行日期升序最多 24 张）+ 从文件导入裁切 + 恢复默认。
- 女优那一屏带「绑定 JavDB」：贴她的演员页链接或编号即可（只取编号，请求一律重组成
  `https://javdb.com/actors/<编号>`），校验读那一页的名字与影片数，绑定是本地写入、
  不联网也能用，并且同时补演员索引行（头像链路要它）。
- 同一屏也带「从日文维基补全」：按她的日文名读档案卡的最新时点，只填编辑弹窗里空着的格子，
  罩杯与已写好的不一致时只提示不覆盖，点保存才写库；没配代理时直接说明缺代理，不发请求。

资料抓取（全部可选、手动触发，绝不自动跑）

- 女优目录分三支全抓（有码 / 无码 / 欧美），页数填 0 = 每支翻到末尾；900 ms 节流 + 502 退避。
- 片商 / 系列编号从影片页解析；身高/生日/三围 JavDB 匿名页已不公布，改从日文维基档案卡取，
  带 Cookie 时优先用 JavDB。档案卡按「最新时点」读（同一页可能留了前后两段年份），三围只收带
  cm 的那一行，生日能吃夹年号的写法。
- 落库形状是定死的：罩杯存一个大写字母（旧程序的下标 1.0…13.0 在启动时一次性换算，实测
  1=A…13=M），身高胸围腰围臀围只存数字（写「160 cm」「85 厘米」都归成 160、85），出身地有
  自己那一列（早先它被写进过中文名）。
- Cookie 只能从本机 Chrome 取得（会话 Cookie 是 HttpOnly）；带坏 Cookie 会让每个端点 502，
  抓取会自动去掉它重试。发布包里绝不含 Cookie。
- 头像三条来路：从 JavDB 下载官方头像、导入头像文件夹 / 压缩包（按文件名认人，支持别名）、
  把图丢进 `actor_inbox\` 开窗口时自动收。已有本地头像可一键写成封面墙封面。
- 头像换完立刻见效，不用重启：每个女优在盘上只有一个固定文件名，所以页面 URL 带着文件的
  修改时间（`?v=`）出去，字节一变 URL 就变；左侧栏、演员详情、封面墙三条写入路径收尾都
  重新取一次引用。版本号只加在页面的 URL 上，库里存的那份引用始终是干净路径。

播放

- 默认交给系统默认播放器（没装 PotPlayer 的机器也能用），「指定播放器程序」是可选项，
  路径无效时自动退回系统默认并写日志。

后台图标

- 设置里「最小化到托盘」开着时，关闭按钮只是隐藏窗口；右键后台图标是显示窗口、重启软件、
  一条分隔线、退出。
- 「重启软件」是本进程重开自己，参数原样带上（包括 `--user-data`），所以重启后落回同一份
  档案、库不会看着像被清空。它换掉的是本次会话读进内存的东西（扫描索引、封面清单、抓取
  连接、界面本身），不用再自己去任务管理器结束任务。

性能（都是实测）

- 图片本地缓存 + 扫描完成时自动预热：网盘图读一次就留一份本地副本，复查只要毫秒级。
- 海报路径的唯一来源是内存扫描索引（一次扫盘答完所有行），不再逐行 readdir 网盘。
- 批量写一律包事务（库切换从 11.7 秒降到实测 525 ms 关 / 523 ms 开）。
- 主进程对磁盘的读写全异步：入库、本地头像导入、备份库、播放前的路径检查都不再同步读盘，
  入库每 25 条让出一次事件循环（否则跑整棵网盘树时窗口会被判无响应）。

## 数据边界

- 读旧程序的库表拿元数据；`movie_` 开头的那些字段一律不改。写旧库仅限 `state_收藏 / state_已看 / state_字幕`
  （值 `真` / `假`，与原程序一致），写回会同步内存缓存。
- 本程序新建的库，条目存在 `JavShelf-data\JavShelf.db`，不会往旧库加表。
- 写影片目录只发生在手动点「保存 nfo / 从 JavDB 覆写」的那些文件，首次会生成 `.nfo.bak`；
  以及勾了「同时写入影片文件夹」的那张封面，覆之前同样先备份成 `.bak`（不勾就只写
  JavShelf 自己的目录）。封面要写到哪个文件由主进程按这条影片自己的文件夹算，界面给不了路径。
- 任何删除都不碰视频、图片与 nfo 文件。删一条记录会连带删掉 JavShelf 自己那份自定义封面，
  但不动影片文件夹。
- 界面交来的路径不再是「程序照办的地址」：读图片文件、导入本地头像只认刚刚在原生选择框里
  挑出来的那些位置，「打开所在文件夹」只认媒体库根目录与 `JavShelf-data` 底下的位置，
  越界一律给出可懂的理由而不是静默失败。
- 指名某个媒体库时不再回落到「碰巧第一个打开的库」：那个库没打开就报错，收藏与删除不会做到
  另一个库上去。
- 设置文件：便携版在 exe 旁边，源码运行在项目目录。`config.json` 里 `javdbCookie` 是登录凭据，
  不要外发。

## 实测（v1.7.1 回归 49 步全绿，样例库 4302 条，两个库 2027 + 2275）

| 项目 | 结果 |
| --- | --- |
| 入库 | 单个本地文件夹 2027 条一次跑完；重复「新增刷新」零改动 |
| 多库索引 | 两个库的两个根目录都在扫描索引里（2027 条 + 2275 条，状态栏「已索引文件 4302」，都不在扫描中）；修复前只剩最后准备的那一棵 |
| 海报墙 | 一页 120 张卡片全出图；滚动 134.6 FPS，中位帧 8.3 ms、p95 16.6 ms、最差帧 20.7 ms，60 帧 0 次停顿、一次扫屏 453 ms（这一步会拒绝挨饿的样本：出帧不足八成或中位帧慢过 34 ms 就重采，三次都不合格直接判失败） |
| nfo 保存回写 | 改片长 + 追加演员 → 盘上那份 nfo 里真的有那个演员、`.bak` 里是覆写前那串原字节、逐字节还原后读回来的不再是刚写进去的值、目录里不留 `.bak` / `.tmp`；番号不存在时写入位置直接被拒。五版以来这个按钮是空转的（演员被丢、`changed:false`），以前那一步只读不写 |
| 删改刷新挡板 | 60 条种子里按「停止」→ 停止为真、删 0 行、库里还是 60 行；把一个根做成读不到 → `shielded` 60、删 0、原样在；换成能读的 → 精确删 3 行、剩 57 行 |
| 残缺索引 | 一个不可读子目录 → 该根保持待重扫、`unreadable` 计 1、阶段序列 `start,scan,incomplete,done`，状态栏写「N 处未读到」 |
| 权限与边界 | `state_时长`（写旧库的第 4 个字段）、库外图片路径、库外「打开所在文件夹」、没打开的库名、没在对话框里挑过的文件路径，五处全部被拒且给出可懂理由；界面文本里旧程序名字命中 0 |
| 单部换封面 | 实测 HR-001（原图 sha256 前缀 `9989869d`）：不勾只换显示（原 poster 前后一致、无 `.bak`）；勾了才覆、`.bak` 里就是原图；再导入不勾不动原文件；「恢复原本封面」回到原字节并把本程序写过的三份全清掉，计数归零。那次副本刷新走的是异步（那张图在网盘上） |
| 查重 | 4302 行比出完全重复 18 组 / 涉及 36 行 / 7 组跨两个库；近似重复用合成行钉死（`ABP-123`+`abp0123`、`SSIS-001`+`SSIS-1` 归一，`ABP-123-2`、`ABP-123A`、只有一份的不报）；一次问 42 个目录，40 个库内目录给出实测体积，`C:\Windows` 与库外路径一律被拒；一次渲染 150 组，「显示更多」到 170，筛选框按番号收窄 |
| 裁切横图与滚轮 | 一张 1200×150 的三色横图进 260×347 的框：按 cover 排版后宽 2776 px 铺满框、缩放地板 0.09366（9.4%）；滚轮向上 `defaultPrevented` 为真且图确实变大；往右拖 4000 px 后图仍盖住框的左右边，纵向那根轴没有余量、锁在中心；点「看全图」整图宽 260 / 高 33 落在框内，再拖一次 X 不变。存出的 300×400 PNG 逐像素采样：左 `[255,0,0]`、中 `[0,255,0]`、右 `[0,0,255]`、上下边 `[0,0,0]`——三个色条都在，多出来的是黑边，与框里看到的同一块 |
| 文件定位 | 抽样 300 条 300/300 定位到真实视频文件（解析结果逐条 `existsSync` 验过，且覆盖到两个库）；其中 299 条同时找到 poster 与 nfo |
| nfo | 读 30 个标签；越界路径写入被拒（`rejected`） |
| 头像缓存 | 头像响应头 `no-cache`（实测 200），海报与手工封面继续吃一年期缓存（实测 200）；同名覆写的那张靠下面的版本号换掉，不靠重启 |
